# Pending conversation skeleton: boundary diagnosis

This is a bounded diagnosis of the existing first-load/reconnect symptom. It reuses r21/r23 evidence and adds an isolated behavior characterization, not another product acceptance, new UI implementation or final checker round. No service or browser was restarted, no old approval card was clicked, and no product source was modified.

## Identified synchronization defect

The current implementation can lose the initial store synchronization when a message response arrives during reconnect:

1. `reconnectToGatewayOperation` creates a local `execServerAgentRuntime` operation **before** refreshing the token. The context's running selector therefore becomes true while the reconnect handshake is pending (`gateway.ts:1597–1630`, `operation/selectors.ts:277–289`).
2. Conversation `useFetchMessages` receives data through `useClientDataSWRWithSync`. Its `onData` returns while that context is running, before writing `dbMessages`, `displayMessages` or `messagesInit` (`data/action.ts:354–421`). This protects streamed content from a lagging DB response but also drops an initial response when the store has no messages.
3. The shared SWR hook sets `hasSyncedRef.current = true` after invoking `onData`, without knowing it returned early (`useClientDataSWRWithSync.ts:63–80`). SWR may now hold the fetched data while the conversation store remains uninitialized.
4. Completing the local operation/rerendering does not reset that ref or guarantee another synchronization for the same cached response. The feedback selector shows a skeleton when `messagesInit` is false, even after streaming becomes false (`resolveMessageListFeedback.ts:19`). A normal remount/refetch can subsequently restore synchronization; this is recovery, not a source fix.

An ignored fixture uses the **actual** Conversation store action, actual SWR sync hook, real React hook lifecycle, chat operation start/complete actions, running selector and feedback function. Only `messageService.getMessages` returns a small synthetic user-message fixture; no provider, DB or Web acceptance is claimed by this probe. One case proves response-during-running → cached data present/store empty → complete/rerender still empty → normal remount populated. A positive case completes reconnect before the response and initializes normally. The fixture does not clear an acceptance browser's store or modify its UI.

## Custom Review reachability

The existing synthetic account **can produce a real custom Review** through `lobe-web-onboarding/showAgentMarketplace`: r22 seeded that tool call into actual runtime, and the real Cloud adapter persisted a mixed custom/binary Review plus a NotificationService token. It did not directly fabricate Review rows.

Its producer advertises `submit_custom`, `skip_interaction`, `stop`, not `cancel_interaction`. The source explicitly reserves cancel until an operation-wide atomic emitter exists across Web/Mobile (`agentInterventionNotification.ts:164–167`). Actual token cancel returned400 without a claim, DB mutation or receiver change. Consequently custom **cancel retry** is unavailable through this real producer, rather than unavailable because the account cannot make a custom Review or lacks a model key. The supported mixed Stop evidence remains separate. No marketplace install/selection or invented allowed action is needed to repeat that conclusion; there is no new executable custom-cancel path to test here.
