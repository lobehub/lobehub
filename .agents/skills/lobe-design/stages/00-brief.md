# Stage 00 · 业务理解（brief）

> 只回答一个问题：**这一页是给谁、为了做出哪个决定或完成哪件事而存在的。**
> 每条 pipeline 的第一步都是这里。产出的 brief 是后续所有 stage 的**必需输入**：视觉、流程、细节、审查都必须引用 brief 的字段来做取舍。

界面做不好，大多不是组件选错了，而是从「表里有哪些字段」或「这类网站一般长什么样」出发去排版。本 stage 先把业务讲清楚，再动界面。

## 聚焦

- 使用者是谁（角色、权限、来意、使用频率）
- 主任务（动词开头），以及用户在这页要做的**关键决定**
- 做决定所需的最少信息，按优先级排序（这就是信息层级的来源）
- 核心对象及其生命周期；能驱动动作的指标和阈值
- 风险：不可撤回、批量操作、涉及钱和权限的写操作
- 页面类型（落地页 / 控制台 / 对话 / 看板 / 文档）和密度倾向
- 视觉型页面另外要清点主体事实和论证（见「subject 模式」）

## 不负责

- 组件、骨架、导入方式 → 30
- 颜色、字号、间距、动效 → 20 / 50
- 状态画面 → 70；文案措辞 → 75
- 不写代码，不改文件。

## 输入

- 用户的指令原文、`route.mjs` 给出的场景和 brief 模式
- 项目层产品事实：仓库根目录的 `.agents/ux/product.md`（如果存在，先读对应模块那一节；装完 / 升级后应由 05-init Round 1 写好）
- 项目层组件用法：`.agents/ux/components.md`（如果存在，结构选型时参考；由 05-init Round 2 维护）
- 路由、侧栏分组、页面 `routes` 文案、tRPC query/mutation、权限点（按需读，读够就停）
- 截图（screenshot-restore 场景）

## 只加载

- [admin-archetypes.md](../references/admin-archetypes.md)：P-01..P-09（只在 archetype 模式下读匹配的那一两个原型）
- [models.md](../references/models.md)：M-01 双钻模型（业务侧）· M-04 Kano 模型（信息优先级）

## 先用模型把问题摆正（M-01 / M-04）

在填模板之前，先用两个模型把「要解决的问题」和「该放什么」摆正。**模型的产出必须落进下面的字段**，只念名字不算完成。

**M-01 双钻模型**——防止拿着一个界面需求直接开始摆字段：

| 阶段 | 要回答的 | 落进哪个字段 |
| --- | --- | --- |
| Discover 发现 | 用户在什么情况下遇到这个问题 | 角色 · 来意 · 频率 |
| Define 定义 | 真正要解决的是哪个问题 | 主任务 · 关键决定 · 决定所需信息 |
| Develop 发展 | 有哪几条解法 | 非目标 + 2 个互斥的解法候选（交给 40 的 L2 定夺） |
| Deliver 交付 | 做到什么程度算完成 | 交给 40 的 L6 验收标准 |

两个判据：**写不出「这次不解决什么」→ Define 没完成**；**只有一个解法 → 还在第一个钻里**。

**M-04 Kano 模型**——裁掉「因为拿得到数据所以放上去」的字段：

- **必备**（缺了不可用）→ 放主区、第一屏
- **期望**（越多越满意）→ 次区、可降级
- **兴奋**（有惊喜，没有不扣分）→ 点缀位，**不能占主区、不能和主动作抢权重**

把「兴奋」属性放进第一屏，是后台页面最常见的错误。

## brief 模式（由路由决定，按任务大小伸缩）

| 模式 | 什么时候用 | 产出 |
| --- | --- | --- |
| `archetype` | 后台 / 看板 / 表单 / 工作流的新建或重做 | 完整模板，带原型编号 P-xx |
| `subject` | 0→1 视觉页 | 完整模板 + 主体清单 + 论证 |
| `compressed` | 已有产品打磨 | 一段话，但必须包含：角色、主任务、关键决定、危险操作、密度倾向 |
| `reverse` | 截图还原 | 从截图反推：这页的主任务、第一视线落点、信息层级 1-2-3 |
| `scope` | 设计系统统一 | 范围（哪些页面）+ 基准页（以谁为准）+ 不在范围内的东西 |
| `reuse` | 上线前审查 | 复用已有 brief；没有就写一段 compressed |
| `project` | 项目接入 / 初始化 | 一行项目级简报：这是什么项目、谁在用、要沉淀什么规则（0 与 05 共用） |
| `lite` | 中等 / 精细指令 | 一行：`页面类型 · 主任务 · 密度倾向`。已有 brief 就直接引用，不重写 |

## 页面 brief 模板（字段名固定，后续 stage 按字段名引用）

```
页面：<路由 / 名称>　　页面类型：<落地页|控制台|对话|看板|文档>　　原型：<P-xx，可多个>
角色：<谁>　来意：<巡检|排障|处置|配置|审核|对账|了解|购买>　频率：<每天多次|每周|偶发|一次性>
主任务：<动词开头的一句话>
关键决定：<看完这页要决定什么>
决定所需信息：1. … 2. … 3. …（这是信息层级，40/50 按它排顺序和权重）
指标：<能驱动动作的指标 + 基准/阈值>；次要指标：<…>
动作：主 <…> / 次 <…>；危险：<动作 — 可撤回? 波及面? 几道确认?>
来路 / 去路：<从哪来，带什么上下文> / <做完去哪>
密度倾向：<高|中|低>（由频率和页面类型推出）
待确认：<推不出来的事实，不要编>
```

### subject 模式附加字段（视觉页）

借鉴 Taste Skill「点子来自主体」：先找出只属于这个主体的东西，视觉方向才不会落到品类默认样式上。

```
主体事实（8–12 条，具体到名词和数字，不写形容词）：1. … 
竞品替换测试：把产品名换成竞品，以下哪几条还成立？成立的不能做主视觉。
论证：每个 section = 一个主张 + 一条证据。写不出证据的 section 删掉。
  S1 主张：…　证据：…
记忆点：访客离开后能复述的那一句 / 一个画面
转化动作：<唯一主 CTA>
```

## 检查清单

1. 主任务是一个动词短语，不是「展示 xx 数据」。
2. 「决定所需信息」按决定排序，不按数据库字段或接口返回顺序排序。
3. 每个指标都说得出「它变坏时用户会做什么」；说不出的标为次要。
4. 每个写操作都标了可撤回性和波及面。
5. 写了密度倾向（后续 50 stage 按它定紧凑程度）。
6. 视觉页：主体事实 ≥ 8 条，且至少 3 条通过了竞品替换测试；每个 section 都有证据。
7. 待确认的事实没有被编造成结论。
8. **M-01**：写了「非目标」，且给了解法候选（≥ 2 个互斥方案）或说明了为什么只有一条路。
9. **M-04**：每个字段标了 Kano 属性；标为「兴奋」的没有占主区。

## 输出

```
[00 · brief] 完成（模式：<archetype|subject|compressed|reverse|scope|reuse|lite>）
<brief 正文，字段名同模板>
下游如何使用：
- 20 方向：读 记忆点 / 主体事实 / 论证
- 30 结构：读 原型 / 决定所需信息 → 区域顺序
- 40 流程：读 主任务 / 关键决定 / 危险 / 来路去路
- 50 视觉：读 页面类型 / 密度倾向 / 决定所需信息（权重）
- 70 细节：读 危险 / 对象生命周期 → 必须覆盖的状态
- 80 审查：读 主任务 / 关键决定 → 「主任务不明」「主路径断裂」两条阻断项
```

brief 一经产出，后续 stage 不重写，只引用；发现 brief 错了，记一条 `遗留 → 00`，在 80 回流时改。
