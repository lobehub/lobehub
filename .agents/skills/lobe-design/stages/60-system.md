# Stage 60 · 设计系统统一（system）

> 只回答一个问题：**多个界面之间，token、组件语法和交互模式是否收敛到同一套。**
> 吸收 Impeccable `normalize` / `extract` 的思路：先盘点漂移、再分诊，最后派发给 30 和 50 去执行。本 stage 只做裁定，不直接改代码。

## 聚焦

- 漂移盘点：裸值、同一角色用了不同 token、同一语义用了不同组件、同一模式有多种写法
- 漂移分诊（借鉴 Impeccable polish 的四分类）：
  1. **缺 token**：系统里没有合适的值 → D-11 缺口，上报设计系统
  2. **一次性实现**：有现成组件 / token 却手写了 → 派发给 30（组件）或 50（取值）
  3. **概念不一致**：同一概念在不同页面叫法、颜色或组件不同 → 先裁定以谁为准，再派发
  4. **局部缺陷**：单页的小问题 → 记录，派发给 50
- 基准裁定：以 brief `scope` 模式里的基准页为准，或以 design.md 的角色表为准

## 不负责

- 单页的业务层级和流程 → 40
- 0→1 的视觉方向 → 20
- 动手修改：组件替换交给 30，取值替换交给 50，本 stage 只出派发清单

## 输入

- 00 brief（`scope` 模式）：范围、基准页、不在范围内的东西（**必需**）
- 全量扫描结果：`node scripts/lint-lobe.mjs <范围> --json`

## 只加载

- [design.md](../references/design.md)：D-01 · D-02 角色表 · D-03 状态色派生 · D-10 执行约束 · D-11 缺口格式
- [components.md](../references/components.md)：C-03 易混组件对照（用于判断「同一语义不同组件」）· C-11 分层边界（判断「同一层内有没有第二个实现」）
- [models.md](../references/models.md)：M-02 格式塔原理（相似性 = 同一分类必须长得一样）

## 步骤

1. 跑 `lint-lobe.mjs --json`，按规则 id 和文件聚合，得到机械漂移的分布。
2. 人工补充脚本看不到的漂移：同一语义用了不同组件、同一概念有不同叫法、同一动作有不同确认强度。
3. 每条漂移按四分类分诊，写清楚以谁为准。
4. 生成派发清单：每条指向 30 或 50，并附上规则 id。
5. 一种写法重复出现 ≥ 2 次、且能被正则识别时，按 [learnings/README.md](../learnings/README.md) 提议升级为 lint 规则。
6. **检查分层重复（C-11）**：同一个原子层组件有没有在项目里出现第二套实现；同一个业务组合有没有在两个地方各拼一遍（相似性要求它收敛成一个项目内组件）。

## 检查清单

1. 每条漂移都有分类和「以谁为准」。
2. 派发清单里每一条都指向 30 或 50，并带规则 id。
3. 缺 token 的情况写成 D-11 缺口，而不是就地发明一个新值。
4. 重复出现的可机械识别模式，已提议升级为 lint 规则。
