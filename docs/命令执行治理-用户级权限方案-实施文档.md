# 命令执行治理：用户级权限方案 —— 实施文档

## 0. 范围与结论

- **控制维度：User 级**，不做 device 级。给某个用户配一份策略，这个用户名下所有执行面统一生效。
- **覆盖的执行面**：
  1. 本机裸跑（desktop，未走 Local Sandbox）
  2. 本机沙箱（desktop，走 SRT 引擎的 Local Sandbox）
  3. ttw connect 连接的远程设备（CLI，和本机沙箱共用同一个 SRT 引擎）
  4. 云沙箱（火山云，lobehub-market）—— **范围收窄**：只做命令文本黑名单（不能跑哪些命令），不做细粒度文件系统 / 网络隔离。原因：火山云沙箱本身就是一次性创建的干净隔离空间，AIO Sandbox 的 REST API（`/v1/shell/exec` 等）也不接受任何策略参数，做不到按次传参，再加一层限制收益不大。
- **两套机制并存，不是一套**：
  - 1/2/3 三个本机 / 设备场景：细粒度策略（读写路径 + 网络域名白名单），走 SRT 引擎，需要新建策略数据模型 + 下发通道。
  - 4 云沙箱：沿用已有的 `command_governance_rules`/`command_execution_logs`（正则 / 前缀 / 精确匹配的命令黑名单），**这套机制已经存在，只差一个收口点没接**（详见 1.4）。

## 1. CPC 仓库（`LobeHub-CPC-Enterprise/lobehub`）—— 主要工作量在这里

### 1.1 数据模型：新建 `user_execution_policies` 表

新增 schema 文件 `packages/database/src/schemas/userExecutionPolicy.ts`，风格参照现有 `commandGovernance.ts`：

```ts
export const userExecutionPolicies = pgTable('user_execution_policies', {
  id: uuid('id').defaultRandom().primaryKey().notNull(),

  userId: text('user_id')
    .references(() => users.id, { onDelete: 'cascade' })
    .notNull()
    .unique(), // 一个用户一份策略，不是多条规则

  enabled: boolean('enabled').default(true).notNull(),

  // 文件系统
  writableRoots: jsonb('writable_roots').$type<string[]>().notNull().default([]),
  readableRoots: jsonb('readable_roots').$type<string[]>(),
  deniedWriteRoots: jsonb('denied_write_roots').$type<string[]>(),
  deniedReadRoots: jsonb('denied_read_roots').$type<string[]>(),

  // 网络
  allowNetwork: boolean('allow_network').default(false).notNull(),
  allowedNetworkDomains: jsonb('allowed_network_domains').$type<string[]>(),

  // 其他
  envAllowlist: jsonb('env_allowlist').$type<string[]>(),
  commandMode: text('command_mode', { enum: ['auto', 'host', 'sandbox'] })
    .notNull()
    .default('sandbox'), // 只要配了策略，默认强制走 sandbox 执行，避免用户绕过

  createdBy: text('created_by'),
  createdAt: createdAt(),
  updatedAt: updatedAt(),
});
```

字段直接对应 `packages/device-sandbox/src/types.ts` 里已有的 `SandboxPolicy`，这样后面组装策略时是直接映射，没有转换成本。

跑 `pnpm db:generate` 生成迁移文件（会接在 `0150_short_darkstar.sql` 之后，比如 `0151_xxx.sql`）。

**没有配置记录的用户 = 不受限**（沿用现有 governance 的 fail-open 哲学，未显式配置策略的用户，`commandMode` 按现有默认 `auto` 处理，行为和现在完全一样）。

### 1.2 服务层：读取策略

新增 `apps/server/src/services/governance/executionPolicy.ts`：

```ts
export const getUserExecutionPolicy = async (
  userId: string,
  db: LobeChatDatabase,
): Promise<UserExecutionPolicy | null> => {
  if (!isGovernanceEnabled()) return null; // 复用现有总开关

  try {
    const [row] = await db
      .select()
      .from(userExecutionPolicies)
      .where(
        and(eq(userExecutionPolicies.userId, userId), eq(userExecutionPolicies.enabled, true)),
      );
    return row ?? null;
  } catch (error) {
    console.error('[governance] getUserExecutionPolicy failed, failing open: %O', error);
    return null; // fail-open，和 checkCommand 保持一致的容错哲学
  }
};
```

未配置 / 查询失败 → 返回 `null` → 客户端按 "无限制" 处理，不影响现有用户。

### 1.3 新增 HTTP 端点：策略下发 + 管理端 CRUD

在已有的 `apps/server/src/router-hono/governance/index.ts` 里加两组路由（复用同一个 Hono app、同一个 `serviceTokenAuth` 中间件）：

```ts
// 桌面端 / CLI 连接时拉取当前用户的执行策略
// GET /api/governance/execution-policy?userId=xxx
app.get('/execution-policy', serviceTokenAuth(), getExecutionPolicyHandler);

// 管理后台 CRUD（一个用户一条记录，用 upsert 语义）
// GET /api/governance/execution-policy/:userId
app.get('/execution-policy/:userId', serviceTokenAuth(), getExecutionPolicyByUserHandler);
// PUT /api/governance/execution-policy/:userId  （新建或更新）
app.put('/execution-policy/:userId', serviceTokenAuth(), upsertExecutionPolicyHandler);
// DELETE /api/governance/execution-policy/:userId （删除=恢复不受限）
app.delete('/execution-policy/:userId', serviceTokenAuth(), deleteExecutionPolicyHandler);
```

`GET /execution-policy?userId=xxx` 是给桌面端 / CLI 用的下发接口，鉴权方式建议直接用**用户已登录的 session token**（不是 `COMMAND_GOVERNANCE_SERVICE_TOKEN`—— 那个是服务间令牌，桌面端 / CLI 是终端用户身份，应该走用户自己的认证），返回结构：

```json
{
  "enabled": true,
  "commandMode": "sandbox",
  "writableRoots": ["~/"],
  "allowNetwork": true,
  "allowedNetworkDomains": ["*.github.com", "*.npmjs.org"],
  "deniedWriteRoots": ["~/.ssh"],
  ...
}
```

或 `{ "enabled": false }` 表示不受限（客户端保持现有行为）。

### 1.4 云沙箱收口点（沿用之前已经定好的方案，命令黑名单）

**`apps/server/src/services/sandbox/service.ts`** —— `SandboxMiddlewareService.callTool()`，加 `checkCommand`/`logCommandExecution` 调用，覆盖 `runCommand` + `execScript` 两个工具名，同时覆盖 "Agent 自动调用"（`builtin.ts`）和 "前台手动执行"（`execInSandboxHandler`）两条路径。这部分不需要 `user_execution_policies` 这张新表，走的是已有的 `command_governance_rules`。具体代码见此前已经给过的方案，不重复贴。

### 1.5 CLI 接线（`apps/cli`）

- `apps/cli/src/tools/shell.ts:64`：
  ```ts
  // 改动前
  const decision = decideSandbox({ deviceNetwork: resolveSandboxNetwork(), mode: resolveCommandMode(), ... });
  // 改动后：连接建立时（下面 1.7 提到的时机）已经把策略拉下来缓存在本地，这里传入
  const policy = await fetchUserExecutionPolicy(); // 新增，内部调用 1.3 的 GET 端点，带本地缓存+失败降级
  const decision = decideSandbox({
    deviceNetwork: policy?.allowNetwork ?? resolveSandboxNetwork(),
    mode: resolveCommandMode(policy?.commandMode), // 关键：把 pushed 参数接上，目前这里传的是 undefined
    ...
  });
  ```
- `apps/cli/src/tools/shell.ts:108`：`createLocalSandboxPolicy(cwd, { allowNetwork })` 改成直接用拉下来的 `SandboxPolicy` 各字段（`writableRoots`/`deniedWriteRoots` 等），不再走死写的 preset。注意 `writableRoots` 至少要包含 `cwd` 和临时目录（沿用现有注释里的理由：编译器 / 包管理器需要写临时文件），拉下来的策略如果没显式包含这两项，客户端要自动补上，避免 "策略配置的人没考虑到工具链需求" 导致功能性 bug。
- 拉取失败（网络问题 / 未登录）时的降级策略：**保守方向**，即 “拉不到策略 = 按当前用户上一次成功拉到的策略执行，仍拉不到（比如第一次连接）就按 `commandMode: 'sandbox'` 的最严格默认值处理，不能静默降级成不受限 \*\*—— 这是一个安全边界，务必和现有 `onUnavailable: 'deny'` 的哲学保持一致。

### 1.6 桌面端接线（`apps/desktop`）

`apps/desktop/src/main/controllers/ShellCommandCtr.ts` 做和 1.5 完全对称的改动（同样调用 `fetchUserExecutionPolicy()`，同样的降级逻辑）。这部分逻辑建议直接抽成一个共享的小工具函数（比如放进 `packages/device-sandbox` 或新建 `packages/execution-policy-client`），desktop 和 cli 两边复用，不要各写一份，避免降级逻辑和缓存逻辑两边不一致。

### 1.7 策略拉取时机

- CLI：`ttw connect` 握手成功后立即拉一次，之后每隔一个固定周期（比如 10-15 分钟）后台刷新一次，同时提供一个 "策略已更新，下次连接生效" 的合理预期（不强求实时热更新，管理员改了策略，等设备下一次连接 / 下一次周期刷新后生效即可，不需要做成推送）。
- 桌面端：应用启动时拉一次 + 同样的周期刷新。

## 3. Market 仓库（`lobehub-market`）

**不需要改代码。**

原因回顾：云沙箱这次范围收窄到只做命令黑名单，而命令黑名单的检查点在 CPC 的 `SandboxMiddlewareService.callTool()`（1.4），发往 market 的 HTTP 请求本身在被拦截的情况下根本不会发出 ——market 收到的永远是已经过滤后的请求，不需要它自己再做一遍判断。之前讨论过的 "火山云 AIO API 不支持传策略参数" 这个限制也不再是阻碍，因为现在压根不需要往 market / 火山云那边传策略。

## 4. 实施顺序建议

1. **Phase 0（先做，独立，收益立竿见影）**：CPC `service.ts` 收口点（1.4），把云沙箱命令黑名单先跑通 —— 这个和用户级细粒度策略完全独立，不用等下面的做完
2. **Phase 1a**：CPC 数据模型 + 服务层 + HTTP 端点（1.1-1.3）
3. **Phase 1b**：Admin 页面 + tRPC（第 2 节），此时可以先用 Postman/curl 验证端到端链路能不能跑通，不用等前端页面
4. **Phase 1c**：CLI + 桌面端接线（1.5-1.7），这一步涉及桌面 / CLI 的发版，节奏上会比前三步慢，需要单独排期

## 5. 验证方式

- 给测试用户配一份策略（比如 `deniedWriteRoots: ['~/.ssh']`），验证：
  - 本机裸跑：Agent 尝试写 `~/.ssh/xxx` 应该被 SRT 挡住，报错信息应该是 "沙箱策略拒绝" 而不是普通的权限错误，方便用户理解
  - 本机沙箱：同上
  - ttw connect 设备：连一台测试设备，同样验证
  - 云沙箱：单独验证命令黑名单（比如配一条 `rm -rf` 的正则拒绝规则），确认前台手动执行和 Agent 自动调用两条路径都被拦
- 验证降级路径：断网情况下重连 CLI，确认走的是 "上次策略" 或 "最严格默认值"，不是静默放开
- 验证 `command_execution_logs`/`user_execution_policies` 相关数据库变化，确认没有影响现有未配置策略的用户（沿用现有 fail-open 验证方式）

## 6. 待确认 / 风险点

1. SRT 网络模型是 "默认拒绝 + 白名单"，做 Admin UI 的时候要设计成 "添加允许的域名" 而不是 "添加禁止的域名"，避免管理员按 TRAE 那种 "默认允许 + 黑名单" 的直觉去配，配出来行为不对
2. 策略下发的刷新周期需要和产品那边对一下能接受的生效延迟（这份文档先按 10-15 分钟给了个参考值）
3. `writableRoots` 自动补全 cwd/tmp 这个逻辑，建议写清楚测试用例，避免策略配置的人不了解底层约束导致工具链跑不起来还以为是 bug
