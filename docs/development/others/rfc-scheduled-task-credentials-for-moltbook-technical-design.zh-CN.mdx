# MoltBook RFC 配套 Technical Design

本文档是 [MoltBook 主 RFC](/zh/docs/development/others/rfc-scheduled-task-credentials-for-moltbook) 的实现级补充，集中说明接口形态、运行时规则、复用的基础设施以及验收方式。

## 1. 设计范围

本文档覆盖以下实现细节：

1. `lobe-scheduled-task` 的 manifest、参数约束、人工确认和 runtime 校验。
2. `lobe-credentials` 的 CRUD 形态、masked /reveal 规则和路径规范。
3. `lobe-cloud-sandbox` 的 env 映射、缺失凭据处理和日志脱敏。
4. dispatcher API、认证、自托管 sidecar 和幂等策略。
5. 复用的存储模型、接口入口、测试矩阵和验收清单。

## 2. Scheduled Task 工具设计

### 2.1 工具操作面

新增包：`@lobechat/builtin-tool-scheduled-task`

提供四个操作：

1. `setScheduledTask`
2. `getScheduledTask`
3. `deleteScheduledTask`
4. `listScheduledTasks`

其中：

1. `setScheduledTask` 与 `deleteScheduledTask` 需要 `humanIntervention: required`。
2. `getScheduledTask` 与 `listScheduledTasks` 保持非 required。

### 2.2 参数形态

`setScheduledTask`

1. create path：必填 `name`、`content`、`cronPattern`
2. update path：必填 `jobId`，并至少提供一个可变字段
3. 可选字段：`agentId`、`description`、`enabled`、`maxExecutions`、`timezone`

`getScheduledTask`

1. 必填 `jobId`

`deleteScheduledTask`

1. 必填 `jobId`

`listScheduledTasks`

1. 可选 `agentId`、`enabled`、`limit`、`offset`

### 2.3 Runtime 规则

1. `agentId` 优先从调用上下文补齐，缺失时失败。
2. `timezone` 默认值为 `UTC`。
3. `maxExecutions` 在 runtime 中统一归一化，支持数字字符串与 `null`，并校验范围 `1..10000`。
4. update path 必须至少包含一个可变字段。
5. create /update path 都接入 `validateCronPatternByDeployment`。

### 2.4 存储与集成

复用现有设施，不新增任务存储系统：

1. 数据表：`agent_cron_jobs`
2. 数据模型：`AgentCronJobModel`
3. 访问链路：既有 cron router /service

前端与服务端集成点：

1. builtin tool registry
2. front-end builtin executor
3. server runtime

### 2.5 返回约定

统一返回 `BuiltinServerRuntimeOutput`，并通过 `state` 提供结构化任务信息，例如：

1. `jobId`
2. `cronPattern`
3. `enabled`
4. `maxExecutions`
5. `timezone`
6. `updatedFields`

## 3. Credentials 工具设计

### 3.1 工具操作面

新增包：`@lobechat/builtin-tool-credentials`

当前实现包含完整 CRUD：

1. `setCredential`
2. `listCredentials`
3. `getCredential`
4. `deleteCredential`

默认启用策略：

1. 最小基线是 `listCredentials + getCredential`
2. `setCredential + deleteCredential` 已实现，可按场景启用

### 3.2 参数与安全规则

1. `setCredential`：必填 `path`、`value`
2. `listCredentials`：可选 `prefix`
3. `getCredential`：必填 `path`，可选 `reveal`
4. `deleteCredential`：必填 `path`
5. `set/get/delete` 都需要 `humanIntervention: required`
6. `additionalProperties: false` 收紧参数面

### 3.3 Runtime 规则

1. `path` 在 runtime 中统一 normalize，并做安全字符校验。
2. `getCredential` 默认返回 masked 值。
3. 只有显式 `reveal=true` 才返回明文。
4. system prompt 优先鼓励按服务命名路径，例如 `moltbook.apiKey`。
5. `sandboxEnv.<ENV_NAME>` 保留为兼容回退路径。

### 3.4 存储与集成

复用现有 secret 基础设施：

1. 存储字段：`user_settings.key_vaults`
2. 模型入口：`UserModel.getUserSettings` / `updateSetting`
3. 加解密链路：`KeyVaultsGateKeeper`

UI 与工具共享同一存储路径，因此写入后可以立即被后续工具和 runtime 消费。

### 3.5 返回约定

统一返回 `BuiltinServerRuntimeOutput`，常见 `state` 字段包括：

1. `path`
2. `valueMasked`
3. `paths`
4. `items`
5. `deleted`
6. `exists`

## 4. Cloud Sandbox 凭据消费链路

### 4.1 Runtime 行为

`lobe-cloud-sandbox` 在 `runCommand` 路径上增加凭据协同能力：

1. 从用户 `keyVaults` 派生可注入的 env 候选。
2. 仅当命令实际引用 `$ENV` 时注入对应变量。
3. 对缺失的 credential-like env 直接失败。
4. 优先返回可执行的修复提示，而不是让任务带空凭据继续执行。
5. 日志与响应保持脱敏，不回显常规明文 secret。

### 4.2 映射规则

默认优先级：

1. `service.<credential_name>`
2. `sandboxEnv.<ENV_NAME>`

例如：

1. `moltbook.apiKey -> MOLTBOOK_API_KEY`
2. 若服务路径不存在，再兼容 `sandboxEnv.MOLTBOOK_API_KEY`

### 4.3 Prompt 侧约束

system prompt 与 runtime 保持一致：

1. 仅在需要时调用 credentials 能力，不做无意义预检。
2. 非用户明确要求时，不使用 `reveal=true`。
3. 缺失凭据时，优先引导写入服务路径。
4. 常规响应不回显明文凭据。

## 5. Dispatcher 与自托管闭环

### 5.1 API

新增接口：`POST /api/agent/cron/dispatch`

请求体：

1. `dryRun?: boolean`
2. `now?: ISO datetime`
3. `maxJobsPerTick?: number`

返回：

1. `tickAt`
2. `jobs[]`
3. `stats`

健康检查：

1. `GET /api/agent/cron/dispatch`

### 5.2 Auth

支持两种认证方式：

1. QStash 签名
2. Bearer Token：`AGENT_CRON_DISPATCH_API_KEY`

### 5.3 执行与幂等

每次 tick 中：

1. 拉取启用任务
2. 基于 `cronPattern + timezone + lastExecutedAt` 判定 due
3. 获取 slot 级幂等锁
4. 调用 `AiAgentService.execAgent(... trigger='cron')`
5. 成功后更新执行统计

锁策略：

1. 优先 Redis
2. 无 Redis 时退化为进程内内存锁

### 5.4 自托管部署

新增环境变量：

1. `AGENT_CRON_DISPATCH_API_KEY`
2. `AGENT_CRON_DISPATCH_MAX_JOBS_PER_TICK`
3. `AGENT_CRON_DISPATCH_CONCURRENCY`

新增 sidecar 约定：

1. `docker-compose/deploy` 默认增加 `cron-dispatcher`
2. `docker-compose/dev` 通过 profile 提供可选 sidecar
3. sidecar 周期性调用 dispatch endpoint

## 6. 测试矩阵与验收

### 6.1 单测与集成测试覆盖

当前应覆盖的重点：

1. `scheduled-task` runtime：create /update/delete /list、参数归一化、cron 策略校验
2. `credentials` runtime：路径校验、masked /reveal、list /set/delete 结果结构
3. `cloud sandbox`：env 注入、优先级匹配、缺失凭据阻断、非 `runCommand` 隔离
4. `dispatch route`：认证、入参解析、健康检查
5. `agentCronDispatcher`：cron 匹配、时区、slot 去重、幂等锁

### 6.2 验收场景

建议至少验证以下场景：

1. 用户写入 `moltbook.apiKey` 后，后台任务能通过 `$MOLTBOOK_API_KEY` 成功执行。
2. 同时存在 `moltbook.apiKey` 与 `sandboxEnv.MOLTBOOK_API_KEY` 时，优先匹配服务路径。
3. 缺失凭据时，任务会收到明确的修复提示，而不是带空值发起请求。
4. `*/30 * * * *` 任务在同一分钟重复 dispatch 时不会被重复触发。
5. self-hosting 环境在部署 sidecar 后能够形成可验证的自动触发闭环。

## 7. 实现说明

当前设计有两个明确边界：

1. 这是现有基础设施上的整合，不是新平台。
2. 长期后台任务的上下文治理仍是后续工作，不在本文档内展开。

因此，本文档描述的是 “如何把能力落地”，而不是 “如何扩展成完整后台编排系统”。
