# Technical Design for the MoltBook RFC

This document is the implementation-focused companion to the [main MoltBook RFC](/docs/development/others/rfc-scheduled-task-credentials-for-moltbook). It captures API shape, runtime rules, reused infrastructure, and acceptance criteria.

## 1. Design Scope

This document covers:

1. `lobe-scheduled-task` manifest shape, parameter constraints, human intervention, and runtime validation.
2. `lobe-credentials` CRUD behavior, masked / reveal rules, and credential path conventions.
3. `lobe-cloud-sandbox` env mapping, missing-secret handling, and log redaction.
4. Dispatcher API, auth, self-hosted sidecar behavior, and idempotency strategy.
5. Reused storage models, integration entrypoints, test matrix, and acceptance scenarios.

## 2. Scheduled Task Tool

### 2.1 Tool Surface

New package: `@lobechat/builtin-tool-scheduled-task`

The tool exposes four operations:

1. `setScheduledTask`
2. `getScheduledTask`
3. `deleteScheduledTask`
4. `listScheduledTasks`

Intervention policy:

1. `setScheduledTask` and `deleteScheduledTask` require `humanIntervention: required`
2. `getScheduledTask` and `listScheduledTasks` do not

### 2.2 Parameter Shape

`setScheduledTask`

1. Create path: requires `name`, `content`, `cronPattern`
2. Update path: requires `jobId` and at least one mutable field
3. Optional fields: `agentId`, `description`, `enabled`, `maxExecutions`, `timezone`

`getScheduledTask`

1. Requires `jobId`

`deleteScheduledTask`

1. Requires `jobId`

`listScheduledTasks`

1. Optional `agentId`, `enabled`, `limit`, `offset`

### 2.3 Runtime Rules

1. `agentId` is backfilled from execution context when possible and fails when unavailable.
2. `timezone` defaults to `UTC`.
3. `maxExecutions` is normalized in runtime, supporting integer-like strings and `null`, then validated in the range `1..10000`.
4. The update path must include at least one mutable field.
5. Both create and update paths apply `validateCronPatternByDeployment`.

### 2.4 Storage and Integration

This design reuses existing scheduling infrastructure:

1. Table: `agent_cron_jobs`
2. Model: `AgentCronJobModel`
3. Access path: existing cron router / service

Integration points:

1. Built-in tool registry
2. Front-end built-in executor
3. Server runtime

### 2.5 Output Contract

Responses use `BuiltinServerRuntimeOutput` with structured task state such as:

1. `jobId`
2. `cronPattern`
3. `enabled`
4. `maxExecutions`
5. `timezone`
6. `updatedFields`

## 3. Credentials Tool

### 3.1 Tool Surface

New package: `@lobechat/builtin-tool-credentials`

Current implementation supports full CRUD:

1. `setCredential`
2. `listCredentials`
3. `getCredential`
4. `deleteCredential`

Default enablement strategy:

1. Minimal baseline: `listCredentials + getCredential`
2. `setCredential + deleteCredential` are implemented and can be enabled by scenario

### 3.2 Parameter and Safety Rules

1. `setCredential`: requires `path`, `value`
2. `listCredentials`: optional `prefix`
3. `getCredential`: requires `path`, optional `reveal`
4. `deleteCredential`: requires `path`
5. `set/get/delete` require `humanIntervention: required`
6. `additionalProperties: false` keeps the parameter surface tight

### 3.3 Runtime Rules

1. `path` is normalized and validated against a safe character set in runtime.
2. `getCredential` returns masked output by default.
3. Plaintext is returned only when `reveal=true` is explicitly requested.
4. System guidance prefers service-scoped paths such as `moltbook.apiKey`.
5. `sandboxEnv.<ENV_NAME>` remains a compatibility fallback.

### 3.4 Storage and Integration

This design reuses the current secret infrastructure:

1. Storage field: `user_settings.key_vaults`
2. Model entrypoints: `UserModel.getUserSettings` / `updateSetting`
3. Encryption path: `KeyVaultsGateKeeper`

Because UI and tools share the same storage path, a successful write becomes immediately available to later tool calls and runtime execution.

### 3.5 Output Contract

Responses use `BuiltinServerRuntimeOutput` with common state fields such as:

1. `path`
2. `valueMasked`
3. `paths`
4. `items`
5. `deleted`
6. `exists`

## 4. Cloud Sandbox Credential Consumption

### 4.1 Runtime Behavior

`lobe-cloud-sandbox` is extended on the `runCommand` path to:

1. Build env candidates from user `keyVaults`
2. Inject only when a command actually references `$ENV`
3. Fail fast on missing credential-like env vars
4. Return actionable repair guidance instead of executing with empty secrets
5. Keep logs and normal responses redacted

### 4.2 Mapping Rules

Matching priority:

1. `service.<credential_name>`
2. `sandboxEnv.<ENV_NAME>`

Example:

1. `moltbook.apiKey -> MOLTBOOK_API_KEY`
2. If the service-scoped path does not exist, fall back to `sandboxEnv.MOLTBOOK_API_KEY`

### 4.3 Prompt-Level Guidance

System prompt guidance is aligned with runtime behavior:

1. Use credential capabilities only when needed
2. Avoid `reveal=true` unless the user explicitly asks for plaintext
3. Prefer repair guidance through service-scoped credential paths
4. Do not echo plaintext secrets in normal responses

## 5. Dispatcher and Self-hosting Closure

### 5.1 API

New endpoint: `POST /api/agent/cron/dispatch`

Request body:

1. `dryRun?: boolean`
2. `now?: ISO datetime`
3. `maxJobsPerTick?: number`

Response:

1. `tickAt`
2. `jobs[]`
3. `stats`

Health endpoint:

1. `GET /api/agent/cron/dispatch`

### 5.2 Auth

Two auth modes are supported:

1. QStash signature
2. Bearer token via `AGENT_CRON_DISPATCH_API_KEY`

### 5.3 Execution and Idempotency

Per dispatch tick:

1. Load enabled jobs
2. Evaluate due status from `cronPattern + timezone + lastExecutedAt`
3. Acquire a slot-level idempotency lock
4. Trigger `AiAgentService.execAgent(... trigger='cron')`
5. Update execution stats after success

Lock strategy:

1. Prefer Redis
2. Fall back to in-memory process lock when Redis is unavailable

### 5.4 Self-hosting Deployment

New environment variables:

1. `AGENT_CRON_DISPATCH_API_KEY`
2. `AGENT_CRON_DISPATCH_MAX_JOBS_PER_TICK`
3. `AGENT_CRON_DISPATCH_CONCURRENCY`

Sidecar convention:

1. `docker-compose/deploy` includes a default `cron-dispatcher`
2. `docker-compose/dev` exposes an optional profile-based sidecar
3. The sidecar periodically calls the dispatch endpoint

## 6. Test Matrix and Acceptance

### 6.1 Unit / Integration Coverage

Key expected coverage areas:

1. `scheduled-task` runtime: create / update / delete / list, parameter normalization, cron policy validation
2. `credentials` runtime: path validation, masked / reveal behavior, list / set / delete result shape
3. `cloud sandbox`: env injection, precedence matching, missing-secret blocking, non-`runCommand` isolation
4. `dispatch route`: auth, input parsing, health inspection
5. `agentCronDispatcher`: cron matching, timezone handling, slot deduplication, idempotency lock behavior

### 6.2 Acceptance Scenarios

Recommended minimum scenarios:

1. After storing `moltbook.apiKey`, a background job can execute successfully through `$MOLTBOOK_API_KEY`.
2. When both `moltbook.apiKey` and `sandboxEnv.MOLTBOOK_API_KEY` exist, the service-scoped path wins.
3. When credentials are missing, execution returns actionable repair guidance instead of sending unauthenticated requests.
4. A `*/30 * * * *` job is not double-triggered by repeated dispatches in the same minute.
5. In self-hosting, the sidecar can produce a verifiable recurring execution loop.

## 7. Implementation Notes

Two boundaries are intentional in this design:

1. This is an integration on top of existing infrastructure, not a new platform.
2. Long-lived background-task context governance remains future work and is not specified here.

This document therefore describes how the capability lands, not how it evolves into a full background orchestration system.
