## 0. 范围结论（比原报告多一块）

原报告的结论是 " 改一个地方（`apps/server/builtin.ts`）就能同时覆盖 `local`/`device` 两个执行目标 "。**这个结论不完整**—— 核实代码后发现，`local`（桌面端自己这台机器）执行文件操作时，压根不经过 CPC 服务端。

### 为什么原报告会漏掉这个

跟这次会话前面已经修过的 `runCommand`/`ShellCommandCtr` 是一模一样的情况：

- `LocalSystemApiName` 声明的 API（`writeFile`/`editFile`/`readFile`/`listFiles`/`moveFiles`/`searchFiles`/`grepContent`/`globFiles`）在**服务端**（`apps/server/src/services/toolExecution/serverRuntimes/localSystem.ts`）统一代理到 `deviceGateway.executeToolCall(...)`，无论 `executionTarget` 是 `local` 还是 `device` —— 这条路径原报告说的没错，`builtin.ts` 加检查确实能覆盖它。
- **但桌面端自己作为 "本机" 执行时，这些 API 根本不通过这条服务端路径**。桌面端渲染进程通过 Electron IPC **直接**调用 `apps/desktop/src/main/controllers/LocalFileCtr.ts` 里的 `@IpcMethod()` 方法（`handleWriteFile`/`handleEditFile`/`readFile`/`listLocalFiles`/`handleMoveFiles`/`handleLocalFilesSearch`/`handleGrepContent`/`handleGlobFiles`），全程不出这台机器，也就不会经过 CPC 服务端的 `builtin.ts`。
- 证据：`apps/desktop/src/main/controllers/GatewayConnectionCtr.ts` 里 `runCommand: (p) => shell.handleRunCommand(p)` 和 `writeFile: (p) => local.handleWriteFile(p)` 是注册在**同一个**网关消息处理表里的 —— 这个表只在 "这台设备被别的会话通过网关寻址" 时才会走到；本机自己聊天时走的是 `LocalFileCtr` 的 `@IpcMethod()` 直连 IPC，跟 `ShellCommandCtr.handleRunCommand` 完全同构。

### 结论

这次要修完整，**需要两处改动**，不是一处：

| 执行目标                                     | 触发路径                                                                   | 需要改的地方                                |
| -------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------- |
| `device`（连接的远程设备，原报告复现的场景） | 服务端 `builtin.ts` → `localSystemRuntime` → `deviceGateway`               | `apps/server`（原报告方案，见第 2 节）      |
| `local`（桌面端自己这台机器）                | 桌面端 `LocalFileCtr.ts` 的 `@IpcMethod()`，全程不出这台机器               | `apps/desktop`（**这次新补的**，见第 3 节） |
| `sandbox`（云端火山云沙箱）                  | 不涉及，维持原报告和之前的决定：云沙箱只做命令黑名单，不做路径级细粒度控制 | 不改                                        |

### 2.2 新增路径检查函数

新建 `apps/server/src/services/governance/pathPolicy.ts`（跟 `policyGate.ts` 平级，不要塞进 `policyGate.ts`—— 那边是 `command_governance_rules` 的逻辑，这边是 `user_execution_policies` 的逻辑，两套数据来源不同，混在一个文件里会让人以为是同一套规则）：

```ts
import type { LobeChatDatabase } from '@lobechat/database';

import { getUserExecutionPolicy } from './executionPolicy';
import { isGovernanceEnabled } from './policyGate';
import type { CommandExecutionTarget } from './types';

export interface PathGovernanceContext {
  apiName: string;
  executionTarget: CommandExecutionTarget; // 只会是 'local' | 'device'，'sandbox' 不走这条检查
  path: string;
  toolIdentifier: string;
  userId: string;
}

export interface PathGovernanceDecision {
  allowed: boolean;
  matchedField?: 'deniedWriteRoots' | 'deniedReadRoots';
}

const WRITE_API_NAMES = new Set(['writeFile', 'editFile', 'moveFiles']);

/**
 * 后缀/子串匹配，不做真正的路径解析 —— 服务端不知道远程设备的真实主目录
 * （方案 A，见文件操作治理-实施指南-20260902.md 第 1 节）。
 * `~/.ssh` 这种带 `~` 的 root，匹配时忽略前缀，只比较 `~` 之后的部分。
 */
export const pathMatchesRoot = (targetPath: string, root: string): boolean => {
  const normalize = (p: string) =>
    p
      .normalize('NFKC') // 全角字符纠正为半角，防御原报告 2.2 那种输入错误
      .replaceAll('\\', '/'); // Windows 分隔符统一成 /

  const normalizedTarget = normalize(targetPath);
  const normalizedRoot = normalize(root).replace(/^~\/?/, '');
  if (!normalizedRoot) return false;

  // 子串匹配：路径里任何位置出现 "/<root>" 或以 "<root>" 结尾都算命中。
  return (
    normalizedTarget === normalizedRoot ||
    normalizedTarget.endsWith(`/${normalizedRoot}`) ||
    normalizedTarget.includes(`/${normalizedRoot}/`)
  );
};

/**
 * 基于 user_execution_policies 的路径检查。跟 checkCommand 一样 fail-open：
 * 功能关闭 / 用户没配策略 / 内部错误，一律放行。
 */
export const checkPath = async (
  ctx: PathGovernanceContext,
  db: LobeChatDatabase,
): Promise<PathGovernanceDecision> => {
  if (!isGovernanceEnabled()) return { allowed: true };

  try {
    const policy = await getUserExecutionPolicy(ctx.userId, db);
    if (!policy) return { allowed: true };

    const isWrite = WRITE_API_NAMES.has(ctx.apiName);
    const deniedRoots = isWrite ? policy.deniedWriteRoots : policy.deniedReadRoots;
    if (!deniedRoots?.length) return { allowed: true };

    const matchedField = isWrite ? 'deniedWriteRoots' : 'deniedReadRoots';
    const hit = deniedRoots.some((root) => pathMatchesRoot(ctx.path, root));

    return hit ? { allowed: false, matchedField } : { allowed: true };
  } catch (error) {
    console.error('[governance] checkPath failed, failing open (allowed=true): %O', error);
    return { allowed: true };
  }
};
```

**需要写的单元测试**（照 `apps/server/src/services/governance/__tests__/policyGate.test.ts` 的风格）：

- `pathMatchesRoot`：全角 `～` 能匹配到半角 `~` 配的规则、Windows `\` 分隔符、`~/.ssh` 精确到子串、不误伤 `/data/backup/.ssh-config`（这个其实会被现在这版后缀匹配误伤，是已知的精度取舍，测试里应该显式写出来 "这是已知局限" 而不是当成 bug 修）。
- `checkPath`：功能关闭时 fail-open、没配策略时 fail-open、DB 报错时 fail-open、命中 `deniedWriteRoots`/`deniedReadRoots` 分别拒绝、只读 API 不查 `deniedWriteRoots`。

1. `logCommandExecution`/`insertLog`（`apps/server/src/services/governance/logsRepository.ts`）现有的参数类型是 `CommandGovernanceContext`，字段是围绕 "命令" 设计的（`commandText` 必填）。2.1 把 `command_text` 改成可空之后，**这两个函数的入参类型和 `insertLog` 的实现也要跟着改**—— 不能像上面伪代码里那样用 `as any` 糊弄过去，正式实现时要给 `CommandGovernanceContext`（或者新增一个 `PathGovernanceContext` 专属的 insert 函数）把 `path`/`matchedField` 也纳入类型，`commandText` 改成可选。建议：`insertLog` 增加可选的 `path`/`policyField` 参数，`commandText` 参数改成可选，两种日志共用一个写入函数，而不是分裂成两个函数 —— 保持 `command_execution_logs` 单表单函数的简洁性。

## 3. 桌面端改动（覆盖 `local` 执行目标 —— 这次新补的部分）

### 3.1 需要新增：一个供桌面端查询用户执行策略的入口

`ShellCommandCtr.ts` 已经建好了 `resolveExecutionPolicy()`/`fetchExecutionPolicy()`（这次会话前面刚做的），通过 `callLambdaMutation(auth, 'executionPolicy.get', undefined)` 拉取 `commandMode` + 细粒度 overlay。**`LocalFileCtr.ts` 应该直接复用同一个 CPC 接口**（`apps/server/src/routers/lambda/executionPolicy.ts` 的 `get` mutation 已经把 `deniedWriteRoots`/`deniedReadRoots` 都带回来了，不需要新增服务端接口），只是要把拉取逻辑从 `ShellCommandCtr` 搬到一个双方都能用的地方，或者在 `LocalFileCtr.ts` 里再实现一份（跟 `ShellCommandCtr.ts` 的 `fetchExecutionPolicy` 代码几乎一样，只是不需要 `commandMode` 字段）。

**建议**：抽成一个共享的小模块（比如 `apps/desktop/src/main/modules/executionPolicy/index.ts`），`ShellCommandCtr.ts` 和 `LocalFileCtr.ts` 都从这里拉取，避免两份几乎一样的 fetch 逻辑分别维护、分别踩坑（这次会话前面 `ShellCommandCtr.ts` 那次实现踩过的坑 ——`storeManager` 默认值、`getTrpcClient`/`callLambdaMutation` 的安全性问题 —— 不要在 `LocalFileCtr.ts` 里重踩一遍）。

### 3.2 路径检查（桌面端可以做到比服务端精确）

新建 `apps/desktop/src/main/modules/executionPolicy/pathPolicy.ts`：

```ts
import { expandTilde } from '@lobechat/local-file-shell/file';

export interface LocalPathPolicyOverlay {
  deniedReadRoots?: string[];
  deniedWriteRoots?: string[];
}

/**
 * 跟服务端 pathPolicy.ts 的 pathMatchesRoot 不同：本机执行时 os.homedir()
 * 就是真实主目录，直接用 expandTilde 精确展开，不需要退化成后缀匹配。
 */
export const isPathDenied = (
  targetPath: string,
  apiName: string,
  overlay: LocalPathPolicyOverlay | undefined,
): { blocked: boolean; matchedField?: 'deniedWriteRoots' | 'deniedReadRoots' } => {
  if (!overlay) return { blocked: false };

  const isWrite = ['handleWriteFile', 'handleEditFile', 'handleMoveFiles'].includes(apiName);
  const deniedRoots = isWrite ? overlay.deniedWriteRoots : overlay.deniedReadRoots;
  if (!deniedRoots?.length) return { blocked: false };

  const resolvedTarget = (expandTilde(targetPath) ?? targetPath).replaceAll('\\', '/');
  const matchedField = isWrite ? 'deniedWriteRoots' : 'deniedReadRoots';

  const hit = deniedRoots.some((root) => {
    const resolvedRoot = (expandTilde(root) ?? root).replaceAll('\\', '/');
    return resolvedTarget === resolvedRoot || resolvedTarget.startsWith(`${resolvedRoot}/`);
  });

  return hit ? { blocked: true, matchedField } : { blocked: false };
};
```

### 3.3 在 `LocalFileCtr.ts` 接入

以 `handleWriteFile` 为例（其余几个 `@IpcMethod()` 照同样的模式加）：

```ts
@IpcMethod()
async handleWriteFile({ path: filePath, content, cwd }: WriteLocalFileParams) {
  const overlay = await this.resolveLocalExecutionPolicyOverlay(); // 3.1 里抽的共享模块
  const decision = isPathDenied(filePath, 'handleWriteFile', overlay);
  if (decision.blocked) {
    await this.reportBlockedFileAccess({ apiName: 'writeFile', matchedField: decision.matchedField!, path: filePath });
    return { error: FILE_BLOCKED_MESSAGE, success: false }; // 具体返回类型要对齐 WriteLocalFileParams 的返回结构
  }

  logger.debug(`Writing file ${filePath}`, { contentLength: content?.length });
  return writeLocalFile({ content, cwd, path: filePath });
}
```

**这里有一个原报告完全没提到、需要新增的东西**：`LocalFileCtr.ts` 跑在 Electron 主进程里，**没有数据库连接**，没法像服务端那样直接 `insertLog`。要把这次拦截记进 `command_execution_logs`，必须**新增一个 lambda tRPC mutation**（比如 `governance.logFileAccess`），桌面端通过 `callLambdaMutation(auth, 'governance.logFileAccess', {...})` 上报，服务端那边再落库。这个 mutation：

- 走用户自己的登录身份鉴权（跟 `executionPolicy.get` 一样，不能用 `COMMAND_GOVERNANCE_SERVICE_TOKEN`）
- 需要在 `apps/server/src/routers/lambda/` 下新增（或者加进已有的 `executionPolicy.ts` 路由文件），内部调用跟 2.3 节 `builtin.ts` 里同一个 `logCommandExecution`/`insertLog`
- 要不要连 "放行" 的也上报，还是只上报 "被拦截" 的？建议只上报被拦截的 —— 放行的每次文件读写都上报会把这张表打爆，服务端 `device` 路径那边 "放行" 其实也没记（`checkCommand`/`checkPath` fail-open 和 "检查通过" 都不写审计表，只写 "blocked=true" 这一种情况，保持一致）

### 3.4 桌面端策略拉取失败时怎么办

跟 `ShellCommandCtr.ts` 的 `commandMode` fallback 不一样 —— 这里的 overlay 只是 "进一步收紧"，参考 `ShellCommandCtr.ts` 已经定下的原则：**拉取失败 = 不叠加限制**（fail-open 到 "无 overlay"），不需要 `commandMode` 那种 "记住上次严格值" 的复杂度，因为路径限制从设计上就是可选的细粒度收紧，不是 "要不要执行" 这种是非题。

## 5. 验证方式

## 6. 施工顺序建议

1. 数据库迁移（2.1）—— 独立，先做，不影响任何现有功能
2. 服务端 `pathPolicy.ts` + 单元测试（2.2）—— 独立开发，此时可以先用假数据跑通逻辑
3. `builtin.ts` 接入（2.3）—— 覆盖 `device`，这一步做完，原报告的复现场景（连接设备上写 `.ssh`）就已经能拦住了
4. Admin 全角字符标准化（4.1）—— 投入产出比最高，可以跟 2/3 步并行做
5. 桌面端共享 fetch 模块 + `logFileAccess` mutation + `LocalFileCtr.ts` 接入（3.1-3.3）—— 涉及桌面端发版，节奏上会比前几步慢，需要单独排期（跟这次会话前面 "细粒度策略要等桌面端新版" 是同一个道理）
6. Admin 审计页面展示新字段（4.2）—— 最后做，不阻塞前面任何一步

## 7. 待确认 / 风险点

1. **后缀匹配的误伤率**：`/data/backup/.ssh-something` 这种巧合路径会被 `deniedWriteRoots: ["~/.ssh"]` 误伤。方案 A 已经是拍板决定，这里只是提醒 —— 如果上线后误伤率超预期，再考虑方案 B（设备上报 homeDir），不要现在就为了防这个小概率场景过度设计。
2. **`logCommandExecution`/`insertLog` 的类型改动**是这次影响面最大的一处代码改动（`command_text` 从必填变可选），改的时候要跑一遍现有 `runCommand` 治理链路的全部测试，确认没有隐式依赖 "`commandText` 一定有值 " 的地方。
3. **桌面端要不要上报 "放行" 的文件访问**：5.3 节建议只上报拦截的，如果后续产品侧想要 "完整的文件访问审计"（不只是被拦截的），这个决定要重新评估 —— 那样的话，几乎每次读写都要发一次网络请求，对本机操作的响应延迟有实打实的影响，需要权衡。
4. **共享 fetch 模块要不要顺手做**（3.1 建议的 `apps/desktop/src/main/modules/executionPolicy/`）：不做也能实现功能，只是会在 `LocalFileCtr.ts` 里重复一份 `ShellCommandCtr.ts` 已经写过、已经踩过坑的拉取逻辑。工作量不大，建议做，但不是阻塞项。
