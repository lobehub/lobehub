# 文件操作（writeFile/editFile）未受命令治理覆盖 —— 错误报告与修复方案

## 0. 结论先行

- **影响范围：仅 CPC 仓库（`LobeHub-CPC-Enterprise/lobehub`）**，不涉及 Admin、不涉及 Market。
- **不是重做架构**，是给现有的治理收口点加一个新的检查维度（按路径检查），复用已有的 `user_execution_policies` 表和 `checkCommand`/`logCommandExecution` 的设计模式。
- **云沙箱不用动**（按你之前的决定：云沙箱本身是干净的隔离空间，只需要命令黑名单，不需要细粒度路径控制）。这份报告的修复范围限定在 \*\* 本机 / 设备（`local`/`device`）\*\* 这两个执行目标。

---

## 1. 复现的问题

**场景**：用户 `user_nOrZkrxaipIg9oXMnMKZIMRQeLl` 在管理后台给自己配置了执行策略（`user_execution_policies`），意图禁止对 `.ssh` 目录的读写。随后在一个连接的远程设备（Windows，`agt_Zii3O0U4LemV` / `tpc_j5LnuLFIjdCf`）上，让 Agent 执行了两个操作：

1. `帮我看一下当前设备的 ～/.ssh 下有什么配置？` —— Agent 用 `Get-ChildItem` 读取，**成功**，且被记录进 `command_execution_logs`（`execution_target=device, blocked=false`）。
2. `帮我往这个路径里面写一个文件，把 test_env：opa_sdasd13daxa 写入进去` —— Agent 用文件写入工具写到 `C:\Users\lijian\.ssh\test_env.txt`，**成功**，且**完全没有出现在 `command_execution_logs` 里**—— 不是 "检查后放行"，是**根本没有被检查**。

用户预期：配置了对 `.ssh` 的写入拒绝策略后，这次写入应该被拦截。实际：完全没拦，也没有任何审计记录。

---

## 2. 根因（三层，独立存在，任何一层单独出现都会导致拦不住）

### 2.1【最根本】文件操作工具和命令执行工具是两个完全独立的 API，治理只覆盖了后者

`packages/builtin-tool-local-system/src/types.ts`：

```ts
export const LocalSystemApiName = {
  editFile: 'editFile',
  getCommandOutput: 'getCommandOutput',
  globFiles: 'globFiles',
  grepContent: 'grepContent',
  killCommand: 'killCommand',
  listFiles: 'listFiles',
  moveFiles: 'moveFiles',
  readFile: 'readFile',
  runCommand: 'runCommand',
  searchFiles: 'searchFiles',
  writeFile: 'writeFile',
} as const;
```

而 `apps/server/src/services/toolExecution/builtin.ts` 里目前的治理白名单：

```ts
const COMMAND_EXECUTION_API_NAMES = new Set<string>([
  LocalSystemApiName.runCommand,
  CloudSandboxApiName.runCommand,
]);
```

`buildCommandGovernanceContext()` 只在 `apiName` 命中这个集合时才会构造治理上下文，进而触发 `checkCommand`/`logCommandExecution`。`writeFile`/`editFile`/`readFile` 等完全不在这个集合里 ——**这类调用从头到尾不会经过任何治理代码，包括审计记录。**

这一条是三层里唯一 "无论如何都会导致拦不住" 的一层，必须修。

### 2.2 规则本身写错了（个例，不是系统性问题，但要顺手改掉）

用户在 `user_execution_policies.denied_write_roots` 里填的是：

```
["～/.ssh"]
```

这个 `～` 是**全角波浪号**（U+FF5E，中文输入法自动转换出来的），不是键盘上的半角 `~`（U+007E）。字符串比较层面这两个字符完全不同，规则永远不会命中任何真实路径。

### 2.3 架构上，`user_execution_policies` 目前只喂给客户端，服务端从不读它

现有的 `user_execution_policies`（`writableRoots`/`deniedWriteRoots`/`deniedReadRoots` 等字段）设计上只有一个消费方：CLI / 桌面端拉取后传给本地的 SRT 沙箱引擎（`createLocalSandboxPolicy(cwd, { overlay })`），用来包裹 `runCommand`/`execScript` 这一个动作的执行环境。**服务端的 `checkCommand()` 从来不读这张表**，它只读 `command_governance_rules`（命令文本黑名单）。

也就是说，即便 2.1 和 2.2 都修好了，如果修复方式是 " 让服务端 `checkCommand` 也去查 `user_execution_policies`"，还需要额外接一条新的判断逻辑 ——`checkCommand` 现在的实现是 "拿命令全文去匹配正则 / 前缀 / 精确规则"，根本不知道怎么用 "路径是否在拒绝列表里" 这种判断方式。这是一个新的检查函数，不是给现有函数加参数那么简单。

---

## 3. 修复方案

### 3.1 新增一个路径检查函数（对齐 `checkCommand` 的设计模式）

在 `apps/server/src/services/governance/` 下新增 `pathPolicy.ts`（或直接加进 `policyGate.ts`），新增：

```ts
export interface PathGovernanceContext {
  apiName: string; // 'writeFile' | 'editFile' | 'readFile' | ...
  path: string; // 目标路径
  executionTarget: CommandExecutionTarget; // 'local' | 'device'（云沙箱不需要这条）
  toolIdentifier: string;
  userId: string;
}

export interface PathGovernanceDecision {
  allowed: boolean;
  reason?: string; // 命中了 deniedWriteRoots 还是 deniedReadRoots
}

/**
 * 基于 user_execution_policies 的路径检查。同样 fail-open：
 * 功能关闭 / 用户没配策略 / 内部错误，一律放行。
 */
export const checkPath = async (
  ctx: PathGovernanceContext,
  db: LobeChatDatabase,
): Promise<PathGovernanceDecision> => {
  if (!isGovernanceEnabled()) return { allowed: true };

  try {
    const policy = await getUserExecutionPolicy(ctx.userId, db); // 复用已有函数
    if (!policy) return { allowed: true };

    const isWrite = ['writeFile', 'editFile', 'moveFiles'].includes(ctx.apiName);
    const deniedRoots = isWrite ? policy.deniedWriteRoots : policy.deniedReadRoots;

    if (deniedRoots?.some((root) => pathIsUnderRoot(ctx.path, root))) {
      return { allowed: false, reason: isWrite ? 'deniedWriteRoots' : 'deniedReadRoots' };
    }
    return { allowed: true };
  } catch (error) {
    console.error('[governance] checkPath failed, failing open (allowed=true): %O', error);
    return { allowed: true };
  }
};
```

**`pathIsUnderRoot` 需要处理的兼容性问题（这是这次修复里最麻烦的一块，务必看完）：**

1. **全角字符**：写入前对路径做 Unicode NFKC 标准化（`str.normalize('NFKC')`），把全角波浪号这类字符自动纠正成半角，从根上堵住 2.2 这种输入错误 —— 这个放在 Admin 保存规则的入口做（见 3.3），检查函数这边也可以再做一次防御性标准化。
2. **`~` 展开**：`~` 代表用户主目录，但服务端根本不知道某个远程设备的主目录路径是什么（Windows 是 `C:\Users\xxx`，Linux/macOS 是 `/home/xxx` 或 `/Users/xxx`）。这里有两个可选方案，需要你定：
   - **方案 A（推荐，实现简单）**：只做**后缀匹配**，不做真正的路径解析。`denied_write_roots` 存的 `~/.ssh` 在检查时转换成 " 路径以 `/.ssh` 或 `\.ssh` 结尾（或路径中包含 `\.ssh\` / `/.ssh/`）" 这种模式去匹配，不管前面是 `C:\Users\lijian` 还是 `/home/alice`。够用，但不精确（比如 `/data/backup/.ssh` 这种巧合路径也会被匹配到，误伤概率低，可接受）。
   - **方案 B（更精确，工作量更大）**：让每个连接的设备在 `lh connect`/ 桌面端启动时上报自己的主目录路径（新增一个字段，设备信息里加 `homeDir`），服务端拿到具体设备的 `homeDir` 后再做 `~` 的精确展开。这个需要改设备注册 / 心跳协议，工作量明显更大，除非误伤率是硬性要求，不建议第一版就做。
   - 这次报告默认按方案 A 写，你要按方案 B 做的话这块要单独排期。
3. **Windows 路径分隔符**：`\` vs `/` 要在比较前统一（比如都转成 `/` 再比较）。

### 3.2 在 `builtin.ts` 接入这个新检查（跟 `runCommand` 那段代码平行，不是复用同一段逻辑）

```ts
const FILE_WRITE_API_NAMES = new Set(['writeFile', 'editFile', 'moveFiles']);
const FILE_READ_API_NAMES = new Set([
  'readFile',
  'listFiles',
  'searchFiles',
  'grepContent',
  'globFiles',
]);

// 在 execute() 里，紧挨着现有的 commandGovernance 那段之后加一段：
if (
  identifier === LocalSystemIdentifier &&
  (FILE_WRITE_API_NAMES.has(apiName) || FILE_READ_API_NAMES.has(apiName))
) {
  const path = String(args?.path ?? '');
  const pathCtx: PathGovernanceContext = {
    apiName,
    path,
    executionTarget: resolveCommandExecutionTarget(identifier, context),
    toolIdentifier: identifier,
    userId: this.userId,
  };
  const decision = await checkPath(pathCtx, this.db);
  if (!decision.allowed) {
    // 复用 COMMAND_BLOCKED_MESSAGE 的写法，给模型一个明确、别再重试的提示
    return {
      content: FILE_BLOCKED_MESSAGE,
      error: { code: 'FILE_ACCESS_BLOCKED', message: FILE_BLOCKED_MESSAGE },
      success: false,
    };
  }
}
```

**这里不复用 `command_execution_logs` 这张表**，因为它的字段是围绕 "命令文本" 设计的（`command_text`/`matched_rule_id` 对应 `command_governance_rules`），跟 "路径 + 命中了 writableRoots 还是 deniedRoots" 这种语义对不上。建议：

- 要么新建一张 `file_access_logs` 表（`user_id, path, api_name, blocked, matched_policy_field, created_at`），跟 `command_execution_logs` 平级
- 要么在 `command_execution_logs` 里加两个可空字段（`path`、`policy_field`），`command_text` 留空，靠 `api_name` 区分是命令类日志还是文件类日志，省一张表

两种都能用，我倾向新建一张表，语义更干净，不用在一张表里塞两种不同形状的数据；但如果你们后台的审计列表页面希望 "命令" 和 "文件操作" 混在同一个时间线里看，那加字段更省事，看你们产品上怎么想。

### 3.3 Admin 侧防御：保存规则时做输入标准化 + 校验

在 `lobehub-admin` 的 `ExecutionPolicyCard.tsx`（或对应的表单提交逻辑）里，保存 `writableRoots`/`deniedWriteRoots`/`deniedReadRoots` 前：

1. 对每个路径字符串跑一遍 `.normalize('NFKC')`，自动纠正全角字符
2. 如果标准化后的值和用户输入的原值不一样，弹一个提示 ("检测到全角字符，已自动转换为：xxx")，让管理员知道发生了什么，而不是静默改写
3. 可以加一条简单校验：路径不能包含全角标点 / 空格（`／`、`＼`、`　`等），不通过就直接拒绝保存并报错，而不是留到运行时才发现规则不生效

这个改动能保证以后不会再有人踩全角字符这个坑，是最值得优先做的一块 ——2.1 的修复解决的是 "能不能拦"，3.3 解决的是 "配错了会不会有人告诉你"。

## 4. 兼容性说明

- **不需要动数据库 schema**：`user_execution_policies` 表现在的字段（`writableRoots`/`deniedWriteRoots`/`deniedReadRoots`）已经够用，直接复用。
- **不需要等桌面端 / CLI 发新版**：这次修复是纯服务端（CPC）改动，跟本机沙箱（SRT 客户端）那条线完全独立 —— 服务端在 `builtin.ts` 这个收口点直接拦截，不依赖设备端是不是更新了。这跟之前 "细粒度策略要等新版桌面端" 的限制不一样，这次修完立刻对所有设备生效，不管设备跑的是新版还是旧版 CLI。
- **不影响云沙箱**：`CloudSandboxIdentifier` 相关的 `writeFile`/`editFile` 不在这次修复范围内，`builtin.ts` 里的判断加了 `identifier === LocalSystemIdentifier` 这个条件，明确把云沙箱排除在外，跟你之前的决定保持一致。
- **未配置策略的用户不受影响**：`checkPath` 和 `checkCommand` 一样 fail-open—— 功能关闭、用户没配策略、内部报错，一律放行，不会因为这次改动导致现有正常用户被误伤。

## 5. 验证方式

1. 给测试用户配置 `deniedWriteRoots: ["/.ssh"]`（先用半角，验证核心逻辑），在一台连接的设备上分别测试：
   - 写 `~/.ssh/xxx` —— 应该被拦截，Agent 收到明确的拒绝提示
   - 写其他路径（比如 `~/Desktop/test.txt`）—— 应该正常写入
2. 故意用全角字符配一条规则，验证 Admin 保存时能拦住 / 提示，而不是静默存进去一条永远不生效的规则
3. 检查审计记录（不管是新表还是新字段）里，这次的拦截 / 放行都有留痕
4. 回归测试：确认 `runCommand` 那条既有的治理链路没有被这次改动破坏（这是修改同一个文件时最容易踩的坑）
